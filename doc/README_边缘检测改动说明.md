# Ti60F225I3_HDMI_Edge

本工程由官方参考工程 `Ti60f225_sc431hai2hdmi_v7`（Efinity 2026.1.132.1.2，
器件 Ti60F225 / I3）复制而来，官方原版完整保留在
`..\_ref\Ti60f225_sc431hai2hdmi_v7\`，本工程内另存有未改动的顶层备份
`rtl\ti60f225_oob_top.v.orig`。

## 先修了厂商 v7 里的三个 debayer bug（颜色问题的根因）

现象：官方 bit 上板后画面整体偏紫，把白平衡增益调到 1.0 后偏色减轻但颜色发灰，
对着红色物体红色显示成绿色。

根因不在摄像头，也不在白平衡调参，而在官方 v7 的 `rtl\debayer\raw_to_rgb.v` 和
`rgb_gain_v1.v` 里。厂商在另一个工程 `Ti60f225_sc431hai2hdmi_isp_v1` 中修好了
这些 bug 并留了注释，但 HDMI demo（v7）用的还是旧版本。两边的模块端口完全一致，
`debayer_top_2to1.v` 也逐行相同，所以是直接替换。

| # | 文件 | v7 的写法 | 修正后 | 后果 |
| --- | --- | --- | --- | --- |
| 1 | `raw_to_rgb.v` | `else if (r_y_cnt[0])` | `else if (!r_y_cnt[0])` | 相位整体错半格，CFA 被当成 G B G B / R G R G 渲染，**红色显示成绿色** |
| 2 | `raw_to_rgb.v` | `w_r_00_00_h0 = r_bayer_00_01_0P_0 + r_bayer_00_00_1P_0`<br>`w_b_00_00_h0 = r_bayer_11_00_1P_1 + r_bayer_01_00_1P_1` | 两条互换 | 偶数行奇列像素的 R/B 整格互换，蓝色区域里 1/4 像素变红，**看上去就是"偏紫"** |
| 3 | `raw_to_rgb.v` | 输出用 `_2P` 级，边界门控用 `!r_de_00_1P` | 输出移到 `_3P` 级，门控用 `!r_de_00_2P`、`r_valid_2P` | 输出窗口比数据早一拍，整行左移 2 像素、行尾丢 2 像素 |
| 4 | `rgb_gain_v1.v` | 奇数行 high←gain_g / low←gain_r，偶数行 high←gain_b / low←gain_g | 奇数行 high←gain_r / low←gain_g，偶数行 high←gain_g / low←gain_b | **白平衡增益施加到了错误的 CFA 通道上**，所以怎么调都调不正 |
| 5 | `ti60f225_oob_top.v` | `dvi_encoder.i_rdata ← hdmi_tx_bdata`，`i_bdata ← hdmi_tx_rdata` | `i_rdata ← alg_rdata`，`i_bdata ← alg_bdata` | 输出级**红蓝对调**：红色物体显示成蓝色，蓝色显示成红色 |

第 5 条说明：`debayer_top_2to1.v` 里 `rgb_datax2_o` 的拼接是
`{b[15:8], g[15:8], r[15:8], b[7:0], g[7:0], r[7:0]}`，低字节是 R，所以顶层串行化后
`hdmi_tx_rdata` 拿到的确实是红色。官方在 `gamma_sel = 0` 这一支却把它接到
`dvi_encoder` 的 `i_bdata` 上，红蓝被对调了。注意 `gamma_sel = 1` 那一支的接线
是**正确**的（`gamma_rdata → i_rdata`），所以只把 VIO 里的 `gamma_sel` 打开就能
在不重新编译的情况下验证这条结论。

已替换：`rtl\debayer\raw_to_rgb.v`（15988 字节）和 `rtl\debayer\rgb_gain_v1.v`
（2231 字节），原来的 v7 版本分别备份成 `raw_to_rgb.v.orig` 和
`rgb_gain_v1.v.orig`。想回退只要把 `.orig` 改回来。

修完之后白平衡应该回到厂商默认的 `r_gain=0x118`、`g_gain=0x0FF`、
`b_gain=0x15E` 再评估，不要停留在 0x0100。

## 显示模式（由 KEY1 循环切换）

| 模式 | 画面 | 用途 |
| --- | --- | --- |
| 0 | 全屏彩色原图（官方直通，RGB888 无损） | 上电默认画面；也是排障基准线，用来区分是摄像头/显示通路问题还是算法问题 |
| 1 | 全屏二值边缘图（黑底白边，全分辨率） | 最直观地看阈值效果 |
| 2 | 左半屏彩色原图，右半屏二值边缘图 | 赛题基础要求里的分屏显示 |
| 3 | 黑底彩色边缘图（按梯度方向配色） | 赛题扩展要求里的"边缘叠加彩色输出" |

模式 0/2 直接透传 de/hs/vs；模式 1 和模式 3 都是对着实时 Sobel 结果直接出图，只
需要边缘标志（不需要原图像素），所以只把 de/hs/vs 延迟 `ALIGN_DELAY = 10` 拍输出。
每种模式下 de/hs/vs 都和该模式自己的像素严格对齐，所以切模式时显示器不会失锁，
只是画面平移几个像素。

排障用的模式 4/5（把行缓存里的原始 RAM 字节直接打到 R/G）已从 KEY1 循环移出，
需要时把顶层 `ui_control` 实例化的 `DIAG_ENABLE` 参数置 1，即可恢复 6 态循环。

按键分配：

| 按键 | 引脚 | 功能 |
| --- | --- | --- |
| KEY1 `key[0]` | GPIOR_22 | 循环切换显示模式 |
| KEY2 `key[1]` | GPIOR_21 | 阈值 −16 |
| KEY3 `key[2]` | GPIOL_03 | 阈值 +16（上限 1024，下限 8） |

KEY0（GPIOL_07）在官方工程里被用作系统复位 `i_arstn`，本工程不动它。
按键默认按低有效（按下接地）处理，如果板上是相反的极性，把
`rtl\image\ui_control.v` 里的 `KEY_ACTIVE_LOW` 参数改成 0 即可。

## 彩色边缘图（模式 3）

- **黑底 + 彩色边**：没有边缘的像素输出纯黑 `00/00/00`，只有通过了阈值的边缘
  才上色。不做原图叠加，因此画面就是一张彩色的边缘图。
- **颜色由 Sobel 梯度方向决定**：|Gx| 明显大于 |Gy| → 红色（垂直边）；|Gy| 明显
  大于 |Gx| → 绿色（水平边）；两者接近 → 对角边，再按 Gx / Gy 的符号是否相同
  分成黄色和青色。四个颜色常量是 `edge_detect_1ppc.v` 里的
  `COL_VERT / COL_HORZ / COL_DIAG_P / COL_DIAG_N`，想换配色改这四行即可；想改
  成"压在原图上"的叠加样式，把 `col_r/col_g/col_b` 的 else 分支改回原图像素即可。
- 走的是**全 1920 列的像素流**，不经过 `split_screen_buffer`，所以没有分屏模式
  （模式 2）那种水平 2:1 压缩，比例是正常的。
- **边缘标志必须用 `edge_valid` 门控**（代码里的 `edge_paint`）。Sobel 每拍都在
  计算，消隐期和每行前几个像素的 3×3 窗口还没填满，那些"垃圾梯度"如果直接拿去
  上色，会出现整行变绿/整行变黄这种故障——仿真里确实踩到过，`tb_edge_detect_1ppc.v`
  现在专门有用例覆盖它。
- 方向判定用的是 `|Gx|` 与 `|Gy|` 的比较：`min > max/2` 判为对角边，所以
  45° 附近的对角边是黄/青，接近水平或垂直的整体仍然是绿/红。

## 相对 VF 工程重写的模块：`split_screen_buffer.v`

VF 板上跑过的版本有三个缺陷，本次已修掉：

1. **跨帧翻转**：原版在每一次 DE 下降沿翻转读写 bank，垂直消隐里多翻了一次，
   导致 bank 配对依赖帧号。新版每行写入的 bank 直接取该行行号的奇偶
   （`orig_y[0]` / `edge_y[0]`），读出 bank 在行尾从显示行号锁存，和帧长、
   流水线延迟都无关。
2. **复位后首帧花屏**：新版用 `primed` 标志，在采满一行之前输出黑场，复位后
   第一行是干净的黑而不是未初始化的 BRAM 内容。
3. **边缘半屏两侧空列**：中值/Sobel 会裁掉 2 个边界像素，边缘流最早从
   `edge_x = 4` 开始，所以写入索引是 2..958。新版把边缘读索引夹到
   `[2, 958]`，最左最右两列显示最近的边缘采样，不再是残留数据。

另外还修了一个 VF 版没有暴露的问题：边缘流比原图流晚约 7 个时钟，如果按
"行尾翻转 bank"来配对，每行最后几个边缘采样会落进下一行的 bank。改用
行号奇偶寻址之后这个问题自然消失。

**2026-10-17：2:1 抽取改成 2 抽头平均。** 原来每行只存偶数列、丢掉奇数列，而分屏
的左右两半都是"完整画面压到半个宽度"，点抽样会让斜边出现明显的像素台阶、细纹变
摩尔纹。现在把相邻两列做 2 抽头平均（`DECIM_AVG=1`，RGB565 的 5/6/5 三个字段分别
相加再右移，避免进位串到相邻字段；每行第 0 列没有左邻居，保持原值），边缘半屏则把
两列的边缘标志做 **OR**，保证 1 像素宽的细边缘不会因为落在奇数列而整条消失。
代价是左半屏水平方向略软一点，换来没有锯齿。把 `DECIM_AVG` 置 0 可以退回原来的
点抽样做对比。

## 已知的、可以接受的行为

- 每帧顶部的第 1 到第 5 行，右半屏（边缘图）显示的是上一帧对应行的残留，
  因为双窗口结构要到显示第 5 行才有合法的 Sobel 窗口。1080 行里占 5 行，
  肉眼基本看不到。
- 第一帧的第一行整行是黑的（缓冲预热），从第二行起正常。
- 分屏模式（模式 2）下左右两半各自显示完整画面，水平方向压缩 2:1（每半屏 960 列
  表示 1920 列），这是 VF 版定下的显示方式，保持不变。两种全屏边缘图（模式 1
  二值、模式 3 彩色）都走流式通路，是**全 1920 列分辨率**，不受这个限制。
- 边缘结果都有恒定的 **2 行垂直偏移**：两个级联 3×3 窗口把行标签推后了 2 行，
  所以画在显示第 d 行的边缘其实是第 d-2 行算出来的。1080 行里占 2 行，肉眼
  不可见；要彻底消掉得给原图再加两级行缓存，性价比不高。

## 2026-10-14 修复：边缘/分屏模式背景发绿、边缘发粉紫（根因：G 通道仍取原始流）

### 现象与结论

| KEY1 按几下 | 显示模式 | 实测画面 | 解释 |
| --- | --- | --- | --- |
| 0 | 1 直通 | 摄像头原图正常 | R/G/B 三路都等价于原始像素，bug 不可见 |
| 1 | 2 全屏边缘 | 白纸时全绿 | 算法输出背景 = 0（R=B=0），G 取的是原始白画面 = 255 |
| 2 | 3 RGB565 回环 | 白纸时全白 | 三路都 ≈ 原始像素 |
| 3 | 4 诊断原始 RAM 字节 | 黄色 + 中间一条绿线 | R = RAM 高字节 = FF，G = 原始白 = FF，B = 0 → 黄 |
| 4 | 5 诊断边缘 RAM 字节 | 全绿 | R = 边缘 = 0，G = 原始白 = FF，B = 0 → 绿 |
| 5 | 0 分屏 | 左白、右绿，左侧有杂色虚影 | G 取的是原始画面**同一屏幕列**的像素，和 R/B 不是同一份数据 |

关键点：**G 通道的数据来源和 R/B 不是同一条流**，所以凡是经过算法的模式都会
出现“背景绿、边缘粉紫、左半屏有虚影”。

### 根因

`rtl\ti60f225_oob_top.v` 里 `dvi_encoder` 的实例化：

```verilog
.i_bdata (gamma_sel ? gamma_bdata : alg_bdata      ),  // 已改到算法输出
.i_gdata (gamma_sel ? gamma_gdata : hdmi_tx_gdata  ),  // ← 漏改，仍是原始相机流
.i_rdata (gamma_sel ? gamma_rdata : alg_rdata      ),  // 已改到算法输出
.i_de    (gamma_sel ? gamma_valid : hdmi_tx_de     ),  // ← 漏改
```

上一轮修 bug 5 时只把 R/B 换成了 `alg_*`，漏掉 G 与 de/hs/vs。参考工程
`sobel\example_top.v` 用 `lcd_data_r = lcd_data_g = lcd_data_b = lcd_data[7:0]`，
三个通道取自同一条流；本工程则是 R/B 走算法输出、G 走原始流。

### 修复

`i_gdata → alg_gdata`，`i_de/i_hs/i_vs → alg_de/alg_hs/alg_vs`（后三个在
`edge_detect_1ppc` 里本来就是等价透传，改只是让意图清楚）。原文件备份为
`rtl\ti60f225_oob_top.v.bak_gfix`。

### 不重编译就能验证根因

把 VIO 的 `gamma_sel` 置 1：那一支路本来就把 `gamma_*`（来源是 `alg_*`）接到
`dvi_encoder`，画面应当立刻恢复正常（色调略偏是 gamma LUT 造成的）。可以在
花十几分钟综合之前先用这个办法确认。

### 边缘 RAM 不是故障原因

`split_screen_buffer` 把边缘值按 16 位拆成两个 8 位 BRAM 存储确实浪费，但它不是
故障原因：诊断 5 的“全绿”是 G 通道造成的，不是 RAM 读出的内容有问题。是否改成
单字节 8 位边缘 RAM 属于后续优化（对 DDR 边缘帧缓存更有意义），与本次故障无关。

## 2026-10-17 移植厂商 ISP：黑电平校正 + 锐化 + 伽马常开

### 为什么做这一步（证据）

对比 `Ti60f225_sc431hai2hdmi_isp_v1`（厂商 ISP 版）和本工程：

- `config/Panel_1080p_reg.mem`（摄像头全部寄存器）**SHA256 完全相同**；
- `raw_to_rgb.v`、`rgb_gain_v1.v`、`debayer_top_2to1.v`、`line_buffer.v` **逐字节相同**。

也就是说摄像头配置和 debayer 是一模一样的。画质差异只能来自厂商 ISP 版多出来的几级
处理。本次只移植其中和"发虚 / 偏色"直接相关的三级，不动 CCM、饱和度、降噪。

### 新的视频链

```
cvo_axi (从 DDR 读出 RAW)
  -> raw_data_blc            黑电平 -17，纯组合，不改时序
  -> debayer_top_2to1        双线性 Bayer->RGB（不变）
  -> rgb_sharpen             亮度 unsharp mask（自带一行缓存，vs/hs/de 与数据一起延迟）
  -> 2:1 串行化 -> edge_detect_1ppc -> gamma_correction(2P2) -> dvi_encoder
```

gamma 原来是 VIO 里的 `gamma_sel` 选的（默认关）。现在**常开**，因为"发灰、暗部偏色"
很大一部分就是没有 gamma。VIO 的那个探针 `gamma_sel` 被改成**锐化旁路**：

| VIO `gamma_sel` | 含义 |
| --- | --- |
| 0（默认） | 锐化开 |
| 1 | 锐化旁路（延迟不变，只是不做 unsharp mask） |

这样可以在板上实时 A/B 对比锐化前后的效果，做报告素材也方便。如果想把探针名字改掉，
在 Interface/Debug 面板里重命名即可，RTL 不用动。

## 2026-10-22 根因确认：Bayer 字节顺序错一列（白变绿 + 边缘锯齿）

对照厂商 **v9** 工程（`..\Ti60f225_sc431hai2hdmi_v9`）：

| 对比项 | 结论 |
| --- | --- |
| `raw_to_rgb.v` / `rgb_gain_v1.v` / `debayer_top_2to1.v` / `line_buffer.v` | **SHA256 完全相同** |
| `config/Panel_1080p_reg.mem`（摄像头配置） | **SHA256 完全相同** |
| VIO 默认增益 | 完全相同（0x118 / 0x0FF / 0x15E） |
| 进 debayer 的像素字节顺序 | **不同** ← 唯一的功能差异 |

v9 顶层：

```verilog
.raw_datax4_i ({ch0_cvo_dout[7:0], ch0_cvo_dout[15:8]})   // 低字节在前
```

本工程原来：

```verilog
.raw_datax4_i (blc_rawdata)                              // = {高, 低}
```

一个 16 bit word 里两个像素的顺序反了，等于把 **Bayer 相位整体错开一列**：
CFA 里 R/B 与 G 的位置全部错配，于是

- 白纸被渲染成**绿色**（G 被当成最亮通道）；
- 双线性 demosaic 在错误相位上插值，边缘出现**拉链状锯齿**；
- 白平衡增益也加到了错误的像素上，所以怎么调都调不出中性白。

**修复**：改成 `{blc_rawdata[7:0], blc_rawdata[15:8]}`，与 v9 一致。

同时为了“只改一个变量”，这次构建把：

- `raw_data_blc.P_BLACK` 临时设为 **0（旁路）**，与 v9 的 RAW 通路完全一致；
- VIO 的 WB 增益恢复成厂商默认 **0x118 / 0x0FF / 0x15E**（这组值是相位正确时标的，相位修好后才重新有意义）。

v9 另外还有 `sensor_clipper.v`（在 CSI 输出处裁成 1920×1080）和 `vid_info_det_v9.v`
（只做时序统计，不碰像素）。本工程时序一直正常，暂时不需要移植。

确认颜色正常后，再把 `P_BLACK` 改回 17，检查暗部对比度是否更好。

## 2026-10-22（二）：gamma 表方向搞错了，画面过暗

`gamma_correction` 的 `2P0..2P4.mem` 是 **x^gamma（压暗）** 曲线，不是提亮。实测（10 bit 表）：

| 曲线 | 输入 256 | 输入 512 | 输入 768 |
| --- | --- | --- | --- |
| `2P0.mem` | 0x040 | 0x100 | 0x240 |
| `2P2.mem` | 0x030 | 0x0DF | 0x220 |
| `2P4.mem` | 0x024 | 0x0C2 | 0x202 |

2P2 把 8 bit 输入 128 映射成 64，等于压暗一半。SC431HAI 的 ROM 已经在 sensor 内部
做了 gamma，再叠一级就是我们看到的“整体很暗”。

**修改**：

- `dvi_encoder` 恢复成 `gamma_sel ? gamma_* : alg_*`，即 **gamma_sel=0（默认）旁路**、
  `gamma_sel=1` 才叠加 2.2，方便现场 A/B；
- `rgb_sharpen.P_BYPASS` 改为常 `1'b0`（锐化常开），不再和 gamma_sel 抢这个探针；
- 若以后确实想加一级轻微 gamma，**`2P0.mem` 是五条里最亮的**（压得最少）。

白平衡在这一版已经调到中性：`r=0xB1, g=0xFF, b=0xB1`（r/g = b/g = 0.694），
后续亮度靠“整体等比缩放 + 是否开 gamma”，不要再破坏这个比例。

## 2026-10-22（三）：Sobel 后加 NMS + 双阈值 + 邻域支撑

### 解决什么

| 现象 | 原来 | 现在 |
| --- | --- | --- |
| 边缘白线很粗 | 幅度阈值没有 NMS，阶跃边缘的梯度脊宽 2–3 px | NMS 沿梯度方向取局部极大值，**压到 1 px** |
| 边缘图白色噪点 | 孤立强梯度直接过阈值 | 双阈值 + 3×3 邻域支撑：**没有任何邻居的孤立像素一律剔除** |
| 白线抖动 | 阈值附近像素反复越界 | 强阈值锚定 + 弱阈值只保留与强边缘相邻的像素，抖动明显减少 |

### 新增文件（需要在 Efinity 里加入 Design 文件列表）

- `rtl/image/sobel_nms.v`

`GRAY_LINE_RAM` 复用现有 IP（幅度 3×3 窗直接调用 `gray_window_3x3`），**不需要新建 IP**。

### 改动文件

| 文件 | 改动 |
| --- | --- |
| `rtl/image/sobel_nms.v` | 新增：3×3 幅度窗 + 4 方向 NMS + 双阈值 + 邻域支撑 |
| `rtl/image/median_sobel_pipeline.v` | Sobel 输出改接 `sobel_nms`，`out_edge` 来自 NMS |
| `rtl/image/edge_detect_1ppc.v` | `ALIGN_DELAY` 10 → **13**（NMS 多 3 拍），流式模式列对齐 |
| `rtl/image/split_screen_buffer.v` | `EDGE_LAST_IX` 958 → 940（NMS 后有效区略缩） |

### 阈值语义

KEY2/KEY3 调的 `threshold` 现在是**低阈值**：

```
LOW  = threshold
HIGH = threshold * 3 / 2
候选 = mag >= LOW，强边 = mag >= HIGH
输出 = NMS 极大值 且 (强边 或 邻居有强边) 且 至少有一个邻居 >= LOW
```

同样的按键位置会比之前**边缘更少一些**（因为多了 NMS 和双阈值），如果觉得边太少，把阈值往下调一档即可。

## 2026-10-22（四）：分屏改为“中线 1:1 切开”

原来的分屏是把**整幅图压缩成两半**（左右各一份完整画面，水平 2:1），需要
`split_screen_buffer` 的 4 个 `GRAY_LINE_RAM`（64 Kb BRAM）做行缓存和 2 抽头平均。

现在按需求改成：

```
屏幕 0   .. 959  : 原图的左半边，1:1 原分辨率
屏幕 960 .. 1919 : 原图右半边的边缘图，1:1
```

实现上**不需要任何行缓存**：原图和边缘流本来就在实时通路上，只要

- 把 `in_r/g/b`、`in_x`、`de/hs/vs` 一起延迟 `ALIGN_DELAY = 13` 拍（和边缘对齐）；
- 用延迟后的列号做 `x < 960` 判断，左半出原图、右半出二值边缘。

| 新：中线切开 | **0** | 13 级延迟线（约 350 FF）+ 比较器，约 20 LUT |

## 2026-10-22（五）：S2 停做 + 7 抽头脊抑制（方案 A）

### 为什么停掉 S2（MHC 5×5 demosaic）

用数值模型（合成红蓝纯色度竖边）比较三种 demosaic 在边缘处的**亮度剖面**：

| 方案 | 边缘处亮度序列 | 结论 |
| --- | --- | --- |
| 真值 | 114 … **90** 90 | 干净阶跃 |
| 双线性（现状） | 114 … **121 → 109** → 90 | 1 次过冲/下冲 |
| MHC 5×5 | 114 … **97 → 121 → 126** → 90 | **振荡更大** |
| MHC + 锐化 0.75 | … **85 → 123 → 137** → 87 … | 最差 |

MHC 的梯度校正项在色度边缘（R/B 反相位变化）上过补偿，反而放大亮度振铃。**S2 按原计划做会让画面更糟，因此不做。**

### 方案 A：7 抽头方向门控脊抑制（已实现）

在 3×3 方向 NMS + 双阈值 + 邻域支撑之后，再加一级：

- **仅对竖直边缘（|Gx| 占优）**启用：比较中心与左右各 3 个像素的 NMS 幅度，只保留最强的一条；
- 横边/斜边**直接放行**——否则一条长横线会被削成单个点（这是实现时踩到的坑，已由 testbench 覆盖）；
- 平局保留最左，保证平坦顶部的脊也只剩一条；
- 代价：**0 额外 BRAM**（6 级 8 bit 移位寄存器）+ 约 20 个比较器；
- `ALIGN_DELAY` 13 → **16**（抑制窗居中需要 3 拍）。

### 仿真

```

   2 px 脊 → 1 px
   相距 3 px 的两条脊 → 只保留较强的一条（1100 保留，1103 消失）
   孤立像素剔除；1 px 竖线保留；2 行横脊 → 1 行且整行完整（111 px 窗口全在）
```

### 已知取舍

- 斜边上的振铃不会被这一级抑制（按方向门控放行）。如果上板发现斜边仍呈"相间带"，再扩成 **7×7 二维**版本（+6 个行缓存）；
- 相距 7 px 以内的两条**真实**竖边会只保留最强的一条，属于此方案的固有代价。

## 2026-10-22（六）：假色抑制（R/B 横向 [1,2,1]/4 低通）

### 定位过程

锐化旁路后（`rgb_sharpen.P_BYPASS = 1'b1`）边缘图明显变细，但**原图彩色边界仍有"红-白-红"条纹**，
说明剩余条纹来自双线性 demosaic 的假色（CFA zipper），而不是锐化。

### 做法

在 `edge_detect_1ppc` 输入端对 **R 和 B** 做 3 抽头 `[1,2,1]/4` 低通，**G 原样保留**：

- `[1,2,1]/4` 在 **2 像素周期处恰好为零**，正是 zipper 的周期，所以能精确抵消它；
- G 不动 → 亮度（0.587G 为主）的细节和锐度完全保留；
- 代价：约 30 个 FF + 2 个加法器，**0 BRAM**，整条流水线延迟 +1 像素（`ALIGN_DELAY` 已按 16 计）；
- 副作用：R/B 的色度细节略微变软，彩色边界可能有 1 像素过渡（肉眼不可见）。

### 仿真

```
tb_edge_detect_1ppc : PASS (162547 checks)
   R/B 为 (a+2b+c)/4、G 为原始值；分屏/边缘/彩色边缘各模式均正确
```

### 若仍有条纹

当前只做了**横向**滤波。竖直彩色边界的 zipper 沿 x 方向，横向滤波即可覆盖；
如果**水平**彩色边界（zipper 沿 y）也出现条纹，再补一级**纵向** `[1,2,1]/4`（需要 2 个行缓存）。

## 2026-10-22（七）：假色抑制升级为可分离二维 + 亮度补偿

上板发现横向 `[1,2,1]/4` 只压掉了 x 方向条纹，竖向条纹仍在，因此补上 y 方向。

### 结构

```
R/B ──► line_buffer(行 y-2,y-1,y) ──► 纵向 [1,2,1]/4 ──► 横向 [1,2,1]/4 ──► + dY ──► 输出
G   ──► line_buffer(同延时)      ──►       直通        ──►      直通       ──► + dY ──► 输出
```

- 两个方向都是 `[1,2,1]/4`，在 **2 像素周期处为零**，正对 CFA zipper；
- `line_buffer` 用现成模块，R/G/B 各一个（每个内部 1 个 `true_dual_port_ram`），共 **+3 个 32 Kb 行缓存**；
- 纵向滤波以 y-1 为中心 → 整条流水线增加 **1 行**延迟；横向以 x-1 为中心 → 再 +1 像素。

### 关键修正：亮度补偿 dY

只滤 R/B 会把亮度里 41% 的成分（0.299R + 0.114B）也一起平滑掉，真实亮度边缘会变软。所以补偿：

```
dY = (77*(R-Rf) + 29*(B-Bf)) >> 8      // 四舍五入
R' = Rf + dY,  G' = G + dY,  B' = Bf + dY
```

加同一个 dY 到三通道，亮度 `0.299R+0.587G+0.114B` 精确保持，而色度仍是滤过的。

**注意必须四舍五入**（`+128` 再右移）：用截断时左右半幅会差 1 LSB，导致 NMS 在水平边上的平局判断劈成两行（仿真实测：横边被拆成左右各半行，1913 → 958/955）。

### 仿真

```
tb_edge_detect_1ppc : PASS (149231 checks)
   水平边：单行 1913 像素（完整，不再被拆成两行）
   2 px 脊 → 1 px；相距 3 px 双脊只留一条；孤立点剔除
   彩色方向配色、中线分屏均正常
```

### 已知

- 画面整体下移 1 行、右移 1 像素（滤波中心偏移），肉眼不可见；
- 行首/行尾各约 2 个像素为滤波边界混合；
- BRAM 占用增加约 96 Kb（3 × 32 Kb），正好用 S1 省下的 64 Kb 抵扣一部分。

## 2026-10-22（八）：去掉亮度补偿（它把 zipper 和噪点加了回去）

上板结果：竖向条纹未改善、原图噪点变多。

原因：`dY = 0.299(R-Rf) + 0.114(B-Bf)` 把**被滤掉的那部分 R/B 原样加回三通道**。
而 CFA zipper 和 sensor 噪点恰好就藏在这个差值里 —— 于是色度虽然平滑了，
**亮度却完全没变**：条纹仍在，还把 R/B 的高频噪声搬进了亮度。

修正：

- **删除 dY 补偿**，滤波后的 R/B 直接送显示和灰度（亮度确实被轻微平滑，这是消 zipper 必须付的代价）；
- **两级 `[1,2,1]/4` 都改成四舍五入**（`+2` 再右移），避免左右半幅差 1 LSB。

### 仿真

## 2026-10-24：竖条根因修复 + 滞后规则收紧

### 竖条/锯齿的真正根因（已修）

`frame_buffer` 的 `.vin` 把 RAW10 的 4 个像素按 **4-3-2-1** 送进 DDR（`{39:32}` 是 Pixel4），
每 4 像素内部左右翻转 → 竖向/斜向边缘呈 4 像素周期锯齿。改成 **1-2-3-4** 后
**竖条和斜边锯齿同时消失**（算法侧一直是对的，合成图自检已验证）。

配套：4 像素反转会翻转 Bayer 列相位，所以字节交换做成 VIO `g_gain[0]` 可切换
（0x00FF / 0x00FE）。

### 抖动与白噪点

sensor 噪声 σ≈1.3 LSB，Sobel 放大 4–6 倍，靠近阈值的像素逐帧跳变 → 线条抖动；
原先的滞后规则"任意 1 个强邻居即放行"会把强边旁的噪声一起提升 → 调低阈值时出现白点。

修正：**弱像素必须至少 2 个强邻居才保留**（细边天然有 2 个，孤立噪点通常 0–1 个）。

### 若仍抖动，按代价从小到大

1. 缩窄双阈值带：`HIGH = 1.15 × LOW`（现在是 1.5×），参数级改动；
2. 边缘灰度再加**纵向** 5 抽头（3–4 个行缓存），噪声再减一半；
3. 终极方案：**时域 2/3 表决**（保持 1 bit/像素的上一帧边缘图，需要 DDR 一帧 259 KB × 2）。
